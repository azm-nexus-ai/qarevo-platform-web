## Release and recovery hardening — 13 November 2026

This is an operational workstream alongside the frozen Stage 2 product scope. It changes no clinical policy, practice membership, payment capability or production hosting. Owner acceptance, live lab review and video remain pending.

Release checks now distinguish three facts: frontend `/api/health/live` reports process liveness and a validated **build-time** source revision; Platform API `/health/ready` checks its required mapped database tables/columns without reading patient rows; Vercel deployment metadata and the actual development alias identify which artifact receives traffic. Frontend liveness is not dependency or clinical readiness. Missing/malformed build identity is `null`, never a fabricated release. Health responses are uncached. API rollout rejects stale revisions, malformed responses and redirects within bounded timeouts. Additive newer schemas remain compatible; equality with the latest Alembic revision is intentionally not required.

### Code rollback procedure

1. Stop further promotion and identify the last **tested** compatible application revisions and their deployment IDs from CI/release evidence. Preserve the failed revision, request references and migration history without exporting secrets or clinical payloads. Previous verified cloud baselines are API `4034ad3c6cde740e5ea5311611acc7f7842d2f7a` and web `be826bfd1068cabdeb7e3a20bbc868df7197ea8b`; these are reference points, not blanket compatibility guarantees.
2. Classify the failure. For a frontend-only regression with a compatible backend, restore the approved frontend deployment to the **development alias** and verify its source identity. Do not invoke a production rollback/promotion or change DNS while repairing development. For an API regression, first check the target code against the current schema and cross-service contracts. A healthy process or an old green build alone is insufficient.
3. Prefer a reviewed revert commit through the normal test/deployment pipeline. A revert has a **new** Git SHA: verify that new SHA, not the original historical SHA. Do not force-push shared branches. Where immediate alias reassignment is needed, record the exact artifact/alias and follow with the equivalent source-control correction.
4. Leave compatible additive schema in place. Do not run an automatic Alembic downgrade, drop tables/columns, restore an older database or relabel a build as a code rollback. Data recovery is a separate controlled operation.
5. Recheck API exact-revision/database readiness, CWS authority/readiness, frontend exact build revision, Vercel READY and the actual development-alias target. Run bounded synthetic role/booking/document smoke checks; deferred live provider tests remain deferred. Record the result before resuming promotion. Existing AI images are usable rollback targets only after their actual runtime artifact has passed the container smoke gate.

### Database recovery procedure and evidence

A **local synthetic logical-restore rehearsal** passed on PostgreSQL 16: `pg_dump --format=custom --no-owner --no-acl` from a newly created source database, then `pg_restore --exit-on-error --single-transaction --no-owner --no-acl` into a separate empty database. All 54 application tables, column definitions/defaults and four linked synthetic identity/profile/appointment/JSON rows matched exactly after restore. A restored foreign key rejected an orphan profile; the validation rollback preserved the checkpoint. The private temporary dump was removed. No existing local application database or hosted Neon database was restored or modified.

This proves the exercised local logical format and fixture, not production backups, power-loss durability, cloud recovery time/data-loss objectives, attachment recovery or cross-service consistency. Before a hosted/production recovery:

1. Name the affected environment, incident owner, approved recovery point, acceptable data loss/time and restore target. Verify backup availability, encryption, access, retention and provider restore support on the **actual chosen infrastructure**. Production RPO/RTO and retention values require owner/clinical/legal decisions; none are inferred here.
2. Restore to a new isolated database/branch with outbound email, AI, payment, media, notification and queue dispatch disabled. Never overwrite the running database as the first diagnostic step; never point the app at an empty restore target before validation. Keep backups and credentials out of Git, browser storage and public CI artifacts.
3. Validate application schema compatibility, constraints, row counts/checkpoint checksums and representative ownership joins. Coordinate Platform API, CWS, AI records, file-object versions and immutable publication/audit evidence at the chosen recovery point; a database dump does not contain S3 objects. Compare post-checkpoint activity before cutover.
4. Reconcile access revocations, password/role changes, appointments, clinical document versions and delivery/payment idempotency records. Invalidate restored human sessions before exposing the recovered environment so an older snapshot cannot silently revive revoked access. Do not blanket-replay restored queues or infer that an email/payment was never delivered from an older database snapshot.
5. Rehearse the candidate cutover and rollback, obtain the required incident/clinical approvals, switch only the explicitly approved target, and verify the same release and role-specific smoke checks. Record measured recovery time and data loss. No real-patient readiness or production disaster-recovery completion is claimed by the local rehearsal.

AI production-image hardening fixes the nonexistent `app` package/entrypoint, excludes environment/IDE files from build context and builds the installed `src.main` runtime as non-root. Its CI smoke runs the real image without network egress or published ports, with mock/disabled providers and workers: liveness must be 200 and unavailable dependencies must produce readiness 503. This verifies a portable release artifact; it does not create an AWS deployment or change the existing FastAPI Cloud AI service.
